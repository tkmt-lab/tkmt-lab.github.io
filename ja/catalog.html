成果の目録

ここでは成果と記録された確認方法を紹介します。公開した一式は人間の専門家による査読を受けておらず、目録への掲載が新しさを確定するものではありません。

研究室が公開したすべての成果を、機械で読める一つのファイルに

/catalog.json は、tkmt-lab が公開したすべての研究と、その中のすべての主張の一覧です。主張ごとに、どんな種類の証拠があるか、Lean の主張文と証明がどこにあるか、どうすれば確かめ直せるか、何を主張していないかを書いています。主な読み手は、成果を見つけ、読み、確かめようとする AI エージェントです。人が読んでも使えます。

目録は新しい事実を足しません。研究室の公開の記録と、各リポジトリの claims.json・AGENTS.md・README.md・CITATION.cff・.zenodo.json から、公開されている状態のものを道具で集めて作ります。元のファイルにない項目は、補わずに省きます。公開のたびに作り直します。正はあくまで各リポジトリです。目録とリポジトリが食い違っていたら、リポジトリが正しく、知らせていただけるとありがたいです。

研究ごとの紹介文と範囲の限定は、llms.txt に合わせた編集文です。個別の主張文・証拠・実行の記録・元の未解決事項は原記録を保ち、元資料での確認状態を残しています。

AI エージェントの使い方

  1. まず catalog-index.json で成果を選び、次に catalog.json の該当する主張を読みます（形式は catalog.schema.json、JSON Schema 2020-12）。主張の番号は変わりません。形は <owner>/<repository>#<claims.json の id> で、例えば tkmt-lab/a3-gsw-classification#thm:classification です。
  2. そのリポジトリの AGENTS.md（entry_points.agents_md）を読み、次に claims.json を読みます。source_revision.commit が release.commit と一致する版を使います。タグは release.tag です。
  3. verification のコマンドを、書かれた作業ディレクトリで実行します。expected_output があれば出力と比べます。Lean の結果は、保存された記録を信じるより、ビルドをやり直すほうが確かです。
  4. 主張を説明するときは、その scope・not_claimed と、研究の scope_flags の範囲を出ないでください。

ファイルの中身

lab研究室の名前、ホームページ、主宰者、連絡先（llms.txt と同じ）。
works[]公開した研究ごとに一つ。id は GitHub のリポジトリ名（tkmt-lab/…）。title はリポジトリが引用に使うよう求めている論文の題（title_tex は TeX の形）。
releaseいまの版のタグ、日付、commit、その版の DOI と全版の DOI。研究室の公開の記録から。
paper_pdf, repo_urlその版の論文の PDF と、リポジトリ。
verification[]リポジトリの README か AGENTS.md に書かれたコマンドを、そのまま写したもの。出典のファイルと節、作業ディレクトリ、書かれていれば期待される出力つき。
scope, not_claimed, scope_flagsその版が示すことと、主張しないこと。scope_flags は claims.json の scope をそのまま写したもの。文章には言語と出典のファイルを付けています。
claims[]claims.json のすべての主張。id、statement、リポジトリ自身の status、evidence[] と evidence_kinds、lean_declarations、scope、not_claimed（残っている課題）、depends_on、リポジトリが書いていれば主張ごとの reproduce、証拠のファイルの場所。

証拠の種類

主張文集には statement_only: true を付けます。statement_lean は定理の型、statement_body は意図した by sorry の仮置きです。元の主張文と証明の URL は参照として分けています。public_proof_reference.executed_by_this_package: false は、この主張文集ではその証明を実行しないという意味です。ビルドが通っても、主張の真偽は確かめられません。

証拠の一つ一つに、種類（kind）と、どの claims.json の項目から読んだか（basis）を書いています。対応が正しいかを確かめられるようにするためです。

lean-proofLean 4 の検査系が確かめた定理。定理名、ファイル、使っている公理、型を書きます。
comparator証明が、別の者が先に書いておいた主張文のファイルとちょうど同じことを証明していることを、Comparator という道具で確かめたもの。kernels 個の独立な検査器が受け入れました。主張文のファイルと、リンクがあれば Comparator の記録を書きます。
independent-implementation別に書いたプログラム、または有限の結果についての別のチームの導出が、同じ結果に達したもの。
prose-proof文章による証明。lean-proof が一緒になければ、機械では確かめていません。independent: true は別のチームによるもう一つの証明です。
ai-review書くことに関わらなかった AI が読み、一部を計算し直したもの。
finite-computation決まった有限の範囲やリストについての、厳密な計算。
numerical-evidence浮動小数点による数値計算。主張を支えますが、証明ではありません。
formal-derivation書かれた仮定のもとでの形式的な（例えば漸近の）計算。証明ではありません。
statement-correspondence元と収録版の定理の型が一致したという保存済みの検査記録。主張の真偽もリンク先の証明も確かめません。目録を作るときは記録とファイルのハッシュを照合し、Lean は実行しません。

例

主張の一項目を短くした例です：

{
  "id": "tkmt-lab/a3-gsw-classification#thm:classification",
  "status": "lean-proved",
  "human_review": false,
  "lean_declarations": ["ClaudeMain.main_full"],
  "evidence": [
    { "kind": "lean-proof", "basis": "lean",
      "declaration": "ClaudeMain.main_full",
      "source_file": "packet/formal/Formal/ClaudeMainFull.lean",
      "axioms": ["propext", "Classical.choice", "Quot.sound"],
      "statement_file": "packet/formal/Formal/ComparatorChallengeMain.lean" },
    { "kind": "comparator", "basis": "README.md",
      "declaration": "ClaudeMain.main_full",
      "statement_declaration": "ClaudeChallenge.main", "kernels": 6, … }
  ],
  "evidence_kinds": ["comparator", "lean-proof", "prose-proof"]
}

限界

目録は、リポジトリにすでに書かれていることを集めるだけで、数学そのものは確かめません。主張ごとに書いてあることが少ないリポジトリもあり（例えば claims.json に主張の文がないもの）、そのときは項目を省きます。研究室の公開の記録には日本語の文もあり、その文には "lang": "ja" を付けています。

検査そのもののやり方と、証拠の種類ごとに言えること・言えないこと：成果をどう確かめるか。
